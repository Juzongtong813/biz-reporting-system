## 1. 范围

本规格只覆盖 V3 P0 工程对齐：成本/订单事实数据生命周期、版本与审计基础、乐观并发、Admin/地市工作区壳、目标路由、共享 URL 上下文，以及旧确认/草稿/锁定流程从正式路径退出。

不在本阶段实施自定义角色、生产部署、默认库迁移、历史报表包物理删除、COS/CFS 切换或生产流量切换。

## 2. 业务规则

1. 成本或订单 Excel 被接收后，系统应自动解析、校验并在同一事务内写入事实、版本和审计，不提供人工确认写入步骤。
2. 警告不阻止写入；结果状态必须明确为“有警告（已生效）”。
3. 任一阻塞错误必须阻止全部事实写入，上一有效事实和版本关系保持不变；失败批次和问题证据仍需保存。
4. 每次在线新增、修改、冲销或成功导入都必须生成版本记录。对同一事实的后续变化必须把前一版本标记为“已被替代”，并建立双向关系。
5. 在线修改和冲销必须携带修改原因。修改请求还必须携带客户端读到的 `expectedVersionNo`。
6. 当 `expectedVersionNo` 与服务器当前版本不一致时，系统必须返回 HTTP 409、稳定错误码 `FACT_VERSION_CONFLICT` 和服务器当前版本摘要，且不得覆盖数据。
7. Admin 与地市版本查询必须由服务端执行角色和地市范围裁剪；地市端不得相信 URL 中的 `cities`。
8. 正式 V3 路由不得出现确认导入、草稿提交、月份锁定/解锁或退回草稿。旧页面仅能保留在无导航入口的 `/compat/*` 隔离路径。
9. `year`、`months`、`cities`、`metric`、`status`、`page`、`sort` 应通过 URL 在 V3 页面间传递；地市端的城市上下文显示为只读绑定值。
10. 在真实隔离 MySQL、浏览器和持久存储证据全部通过前，`DEPLOYMENT_GATE=BLOCKED`。

## 3. EARS 验收标准

- 当上传文件不存在阻塞错误时，系统应原子写入全部事实、版本和审计，并返回 `current_effective` 或 `effective_with_warning`。
- 当上传文件仅包含非阻塞警告时，系统应写入全部合法事实并返回警告摘要，且所有新版本应标记为 `effective_with_warning`。
- 当上传文件包含任一阻塞错误时，系统应返回 `validation_failed`，并保持事实行数、当前版本和替代关系不变。
- 当用户保存在线修改时，系统应要求非空修改原因和 `expectedVersionNo`，并生成下一版本及前后值差异。
- 当并发请求使用过期版本号时，系统应返回 409 和当前版本摘要，并保持服务器数据不变。
- 当查询版本列表或详情时，系统应返回当前有效/有警告/已被替代状态、来源、修改原因、前后值和前后版本关系。
- 当地市用户访问版本接口时，系统应仅返回 JWT 绑定地市的数据。
- 当用户从正式导航进入 V3 工作区时，系统应只展示目标信息架构，并在页面跳转时保留共享 URL 上下文。
- 当旧 URL 被访问时，系统应重定向到 V3 目标页；只有显式 `/compat/*` URL 可以加载旧流程。

## 4. 验收证据分层

- 本地工程证据：类型检查、构建、迁移文件校验、迁移账本回归、API 集成测试、路由静态门禁。
- 浏览器证据：1366x768 与 1440x900 下目标路由、上下文保留、版本列表/详情、自动生效与冲突反馈。
- 部署证据：隔离真实 MySQL、真实持久存储、备份恢复和浏览器联调。该层本轮缺失时不得解除部署门禁。
