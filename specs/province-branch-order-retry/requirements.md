# 省级直属订单与失败批次修正需求

## 范围

本变更解决两个订单导入问题：

1. 订单源文件的“地市名称”可能为“山东省分公司”，系统必须将其作为省级直属经营单位处理，并保持合同、额度、费率、统计和权限隔离。
2. 待维护订单必须能够下载、线下修正后作为新批次重新上传；新批次接替旧失败行，不能重复入账，也不能删除原始审计数据。

## 用户故事

- 作为省级管理员，我可以为山东省分公司配置合同分配额度和月度费率，使其订单独立核算。
- 作为省分公司账号，我只能访问山东省分公司经营单位的数据。
- 作为地市账号，我不能查看或操作山东省分公司订单。
- 作为订单管理员，我可以下载某批次的待维护订单，线下修正后作为新批次上传。
- 作为审计人员，我可以追溯原失败行、新修正行、来源批次和操作账号。

## 验收标准

### R1 省级直属经营单位

- 当订单的省份为山东省且地市名称精确匹配“山东省分公司”或已配置别名时，系统应将订单映射到类型为 `province_branch` 的山东省分公司经营单位。
- 当省分公司订单的合同不存在、合同未分配该经营单位或业务月份无有效费率时，系统应保留原始行并标记为 `needs_review`，不得进入经营统计。
- 当省分公司订单通过全部校验时，系统应关联具体合同、独立额度和费率，并计入山东省汇总一次。
- 当展示地市对比或合同分配时，系统应将山东省分公司标记为“省级直属”，不得伪装成普通地市。

### R2 权限隔离

- 当账号数据范围为某个普通地市时，系统应拒绝其读取、下载或维护山东省分公司订单。
- 当账号数据范围为山东省分公司经营单位时，系统应只返回该经营单位的数据。
- 当账号数据范围为山东省时，系统应返回省内普通地市和省级直属经营单位数据。
- 所有下载、上传、接替、合同分配和费率操作均应写入审计日志。

### R3 失败订单导出

- 当订单批次存在 `needs_review` 行且操作人有导出权限和数据范围时，系统应生成一个单工作表 XLSX 文件。
- 导出文件应只包含当前可见的待维护行，不得包含已成功订单。
- 导出文件应保留标准 34 个业务列，并附加原批次 ID、原订单行 ID、原行号和错误原因等修正元数据。
- 未授权账号不得下载超出其经营单位范围的数据。

### R4 修正文件作为新批次上传

- 当用户上传带有效修正元数据的文件时，系统应创建新的修正批次，并复用正常订单校验流程。
- 当修正行成功写入新批次时，系统应将被接替旧行标记为 `superseded`，保留原始内容和接替关系。
- 当修正行仍未通过校验时，最新修正行应成为新的 `needs_review` 行，旧行仍保留为 `superseded`。
- 当修正文件包含非来源批次待维护行、已接替行或无权限行时，系统应拒绝该行，不能影响其他订单。
- 当普通订单文件不包含修正元数据时，系统应维持当前导入行为。

### R5 防重与统计

- 同一修正文件不得重复导入。
- 被接替行不得参与经营统计、待维护数量或超额计算。
- 新批次有效行只能计入一次。
- 普通地市订单导入、合同统计、年度/月度筛选和审计日志不得发生回归。

### R6 发布门禁

- 在任何 CloudBase 部署前，系统必须通过类型检查、构建、自动化测试和本地 API 验证。
- 在任何 CloudBase 部署前，必须启动本地前后端，并由用户在 Codex 内置浏览器完成约定的人工测试。
- 只有用户明确确认“本地测试通过，可以部署”后，才能执行 CloudBase 数据库迁移和发布。
