# 经营数据中台总纲

> 状态：当前权威总纲  
> 生效日期：2026-07-25  
> 说明：本文基于用户最新目标、仓库只读审计和真实地市测算模板重建。此前同名文件、旧 overview、旧 memory、旧交付报告和旧任务勾选仅保留为历史证据。

## 1. 权威顺序

发生冲突时，按以下顺序裁决：

1. 用户最新目标与明确要求。
2. 经用户确认的“架构目标与范围确认”。
3. 本总纲及以下两组新规格：
   - `specs/operating-data-platform/`
   - `specs/larkmidtable-architecture-optimization/`
4. 代码、数据库、部署和运行证据，用于说明现状，不自行定义目标。
5. 旧 overview、memory、delivery report、历史规格和旧 tasks，仅作为可追溯证据。

任何历史任务勾选、部署声明或交付结论，都不得直接转换为新任务的完成状态。新任务只有在对应需求、设计和当前验收证据同时满足后才能勾选。

## 2. 平台定位

经营数据中台是“山东区域经营数据汇聚、治理、发布与服务平台”。它不是单一报表页面、Excel 搬运工具或目录整理项目。

平台以地市经营工作为入口，把合同主数据、月度完工与审定、成本计划、人员驱动、综合代维、年度预测、人工调整和未来外部系统数据纳入同一条可追溯链路，并向 Web、小程序、导出、经营分析、只读 BI 和只读 AI 提供一致的数据服务。

## 3. 已确认的架构目标

1. 保留当前 NestJS、React、Vite、pnpm workspace、CloudRun 和 CloudBase MySQL，先演进为边界清晰的模块化单体。
2. 不以 LarkMidTable 或其他外部项目作为权威；只借鉴可验证的分层、装配和仓库治理思想。
3. 所有来源统一进入“接收、解析、标准化、校验、差异预览、确认发布、快照、血缘审计”生命周期。
4. 原始输入、标准记录、已发布事实和派生指标必须分离，页面展示不等于数据真相。
5. 手工填报、文件上传和未来 API 同步使用同一组业务校验、发布规则、权限模型和指标定义。
6. 采用渐进迁移，不进行大爆炸重写，不用历史完成声明替代回归证据。

## 4. 真实业务对象

真实地市测算模板证明，一个上传文件是一个“经营测算包”，而不是若干互不相关的工作表。测算包至少包含：

- 合同转化：合同身份、合同条款、累计金额、年度预测、经营假设和派生毛利。
- 合同月度：合同与月份维度的立项完工、验收审定及后续可扩展的订单、开票数据。
- 成本测算：成本类别、月份、金额及人员等经营驱动。
- 综合代维：合同维度的跨年度累计开票、有效月份、月均差异和派生毛利。

平台必须显式区分：

- `actual`：已发生并可核验的数据。
- `forecast`：预测或计划数据。
- `assumption`：暂定费率、管理费、有效月份等假设。
- `derived`：按版本化指标公式计算的数据。

## 5. 核心不变量

### 5.1 来源与血缘

每项标准记录和正式指标必须能追溯到来源文件哈希、工作表、行号或单元格、接入批次、操作者、地市、期间、场景、模板版本、标准化规则和发布版本。

### 5.2 值语义

空白、明确填报零、公式计算零、不适用和解析失败是不同状态。平台不得用数据库默认值或 `?? 0` 抹平这些差异。

### 5.3 单位与期间

金额必须保存原始单位和标准单位；期间必须保存年度、月份、截止月份和场景。公式中的魔法数字不得代替期间元数据。

### 5.4 主数据

合同编码不是永远可靠的单一键。组合编码、别名、历史编码和非标准编码必须通过主合同、合同别名和人工确认的映射关系治理。

### 5.5 指标

Excel 公式和缓存值是来源证据，不是生产执行代码。正式指标由受控、可版本化、可测试的指标定义计算，并与来源结果对账。

### 5.6 发布

正式数据只能从通过校验的批次发布。发布必须幂等、可审计、可回放并生成不可变版本；回滚通过新版本或显式撤销事件完成，不直接改写历史证据。

### 5.7 权限

`city_user` 只能处理自身地市范围，`system_admin` 的跨地市操作必须审计。任何客户端传入的地市、操作者或发布归属都不能覆盖认证上下文和批次自身上下文。

## 6. 目标分层

1. 来源层：Excel、Web 手工填报、小程序、合同主数据、未来 OA/ERP/API。
2. 接入层：源文件、根批次、子数据集、模板适配器、原始记录、幂等键。
3. 治理层：标准化、单位换算、主数据映射、质量问题、指标定义、审批与审计。
4. 资产层：合同主数据、地市年度计划、合同月度值、成本月度值、综合代维期间快照、发布快照。
5. 服务层：查询、指标、质量、导出、血缘、版本和权限过滤 API。
6. 应用层：地市 Web、管理员 Web、小程序、经营分析、只读 BI、只读 AI。

第一阶段不要求物理拆库。逻辑边界、依赖方向、表语义和发布协议必须先稳定，再根据规模决定是否拆分基础设施。

## 7. 规格职责

### 7.1 本总纲

定义平台定位、权威顺序、长期不变量、规格边界和阶段门禁。

### 7.2 operating-data-platform

定义业务能力、数据生命周期、概念数据模型、质量规则、发布规则、权限、数据服务和迁移验收。

### 7.3 larkmidtable-architecture-optimization

定义代码与仓库如何支撑中台：模块边界、依赖方向、装配、共享契约、前端结构、测试门禁、归档和渐进迁移。

### 7.4 database-architecture-v3

定义 CloudBase 现有数据库事实基线、目标物理模型、001-010 迁移边界、历史数据治理、对象存储、蓝绿切换、恢复和回滚门禁。

三组规格不能互相覆盖。业务语义冲突以中台规格为准；软件落位冲突以架构规格为准；物理 schema 与数据库迁移冲突以数据库架构规格为准；三者与本总纲冲突时以本总纲为准。

## 8. 当前实施范围

第一实施范围包括：

1. 固化可重复的代码、数据库、模板和测试现状基线。
2. 建立经营测算包的根作业与子数据集模型。
3. 建立原始记录、标准记录、质量问题、合同映射、值状态、单位、场景和期间模型。
4. 建立差异预览、原子发布、版本快照和血缘审计。
5. 用真实模板建立适配器与回归夹具，但不把单一模板结构硬编码为永久业务模型。
6. 渐进迁移现有地市上传、手工填报、查询、看板和导出到统一服务层。
7. 建立架构依赖检查、统一测试入口和历史产物归档规则。

## 9. 当前非目标

- 不迁移到 Java、Vue、Maven 或新的 ORM、状态管理和构建系统。
- 不立即引入 Flink、Kafka、Doris、ClickHouse、DataX、Iceberg 等重型组件。
- 不允许 BI、AI 或外部工具绕过权限和发布数据集直接写生产表。
- 不在文档重建阶段执行生产 DDL、数据修复、部署或真实业务写入。
- 不一次性删除或搬迁全部历史产物。
- 不因架构重建顺带进行无关视觉改版。

## 10. 阶段门禁

1. 文档门禁：七份权威文件完成交叉检查并由用户确认。
2. 基线门禁：现状能力必须有当前代码、测试或只读运行证据，历史声明单独标记。
3. 设计门禁：任何 schema、API 或目录迁移先有需求编号、设计和回滚策略。
4. 实施门禁：任务清单确认后才能改代码；生产动作必须另行明确授权。
5. 验收门禁：构建通过不等于业务完成，必须同时通过契约、权限、数据质量、迁移和真实场景验收。
