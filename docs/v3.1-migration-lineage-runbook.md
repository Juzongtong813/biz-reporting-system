# V3.1 迁移与事实文件血缘运行手册

## 安全边界

- 应用启动不执行迁移；生产环境 `DB_SYNC=false`，TypeORM `synchronize=false`。
- 生产迁移必须显式设置 `MIGRATION_APPROVED=true`，并单独执行迁移命令。
- `schema_migrations` 记录迁移版本、文件名、SHA-256、状态、执行方式、耗时与错误。
- 已执行迁移文件不可修改；新增变更必须追加新的 SQL 文件。
- 本手册中的隔离验证不得使用生产数据库主机、数据库名或账号。

## 迁移检查与验证

SQL 文件清单和基础格式检查：

```powershell
pnpm migration-files:check
```

该命令只检查迁移文件清单、命名、顺序和基础格式，不连接 MySQL，不代表 MySQL 兼容验证。

真实 MySQL 隔离验证必须使用具备临时建库、删库权限的非生产账号：

```powershell
$env:NODE_ENV='test'
$env:MIGRATION_TEST_MYSQL_HOST='127.0.0.1'
$env:MIGRATION_TEST_MYSQL_PORT='3306'
$env:MIGRATION_TEST_MYSQL_USER='...'
$env:MIGRATION_TEST_MYSQL_PASSWORD='...'
pnpm test:migrations:mysql
```

脚本要求四个 `MIGRATION_TEST_MYSQL_*` 变量全部显式存在，不回退到 `DB_*`、默认主机、默认端口或默认账号。脚本创建带时间戳和进程号的临时数据库，依次执行 `precheck -> up -> status -> 第二次 up -> status`，断言 001 至 006 迁移账本、历史结构 adopt、005/006 表列与索引、二次执行幂等；另建故障注入临时库，验证失败迁移留下 `failed` 账本和定位信息。成功或失败后删除全部临时库，并从 `information_schema` 确认删除。没有可用的非生产凭据时，该门禁必须标记为阻断，不能用 `migration-files:check` 替代。

生产部署窗口内的迁移命令仅在审批和备份完成后执行：

```powershell
$env:NODE_ENV='production'
$env:DB_SYNC='false'
$env:DB_TYPE='mysql'
$env:DB_HOST='...'
$env:DB_PORT='3306'
$env:DB_USERNAME='...'
$env:DB_PASSWORD='...'
$env:DB_DATABASE='...'

pnpm db:migrate:precheck
pnpm db:migrate:status
$env:MIGRATION_APPROVED='true'
pnpm db:migrate
pnpm db:migrate:status
```

## 隔离集成验证

```powershell
$env:FACT_REFERENCE_ROOT='E:\code2\biz-reporting-design-v2\参考数据'
pnpm test:facts-v31
pnpm test:storage-gate
```

事实数据脚本创建临时 SQLite、原文件目录和随机端口 API，结束时自动停止服务并删除全部临时文件。存储门禁脚本验证生产环境缺少路径、路径错误或缺少真实 Linux 挂载点时都会拒绝启动。

## 原始文件持久卷

- 生产固定目录为 `/mnt/fact-source-files`，环境变量必须显式设置 `FACT_SOURCE_STORAGE_ROOT=/mnt/fact-source-files`。
- Docker 镜像用 `com.biz-reporting.required-persistent-mount` 标签声明该挂载契约；容器内目录本身不视为持久存储。
- CloudBase 云托管必须在控制台为 API 服务启用存储挂载，将独立 COS 存储桶目录或 CFS 挂载到 `/mnt/fact-source-files`。现有 `cloudbaserc.json` schema 不表达该挂载，控制台挂载是部署门禁，不能省略。
- 启动时检查环境变量、绝对路径、Linux `/proc/self/mountinfo`、读写权限和落盘同步；任一失败即拒绝初始化事实文件存储。
- 文件按 SHA-256 内容寻址：`<前两位>/<64位SHA-256>`，使用独占创建并在重复写入时复验哈希。
- 原文件不自动删除，与导入批次同生命周期保留。任何清理策略必须保留审批记录并证明血缘不再需要回查。

CloudBase COS 挂载操作参考官方文档：`https://docs.cloudbase.net/run/deploy/configuring/storage/cos`。挂载完成后必须在运行实例中确认 `/mnt/fact-source-files` 是独立挂载点，而不是容器临时层。

## 备份与恢复

- MySQL 备份与原始文件卷必须使用同一备份周期、同一保留周期和同一恢复点标识。
- 恢复时先选择同一恢复点，恢复数据库和文件卷，再执行批次 SHA-256 抽样回查；任一侧恢复失败或时间点不一致，不得开放导入和原文件下载。
- 备份验收必须同时记录数据库账本版本、文件卷快照标识和恢复演练证据。

## 上线顺序与回滚

1. 冻结迁移 SQL，完成同恢复点的数据库备份和事实文件卷快照。
2. 使用生产同版本的隔离 MySQL 执行 `precheck -> up -> status -> 第二次 up -> status`。
3. 在 CloudBase 配置并核验 `/mnt/fact-source-files` 持久挂载，运行存储门禁。
4. 在生产库只执行 `precheck` 和 `status`，确认无 checksum drift、failed 或 partial 状态。
5. 在批准的部署窗口设置 `MIGRATION_APPROVED=true`，执行一次迁移并再次查询状态。
6. 发布 API，验证上传、下载审计、幂等、失败回查、地市隔离和 Admin 汇总。

回滚不自动删除事实表、血缘列或原文件。应用回退时保留新增表、列和文件证据；迁移失败时先依据 `schema_migrations.error_message` 定位，按同一恢复点恢复数据库与文件卷，再追加修复迁移。禁止修改已执行 SQL，禁止在存在事实数据后直接 `DROP TABLE`。
